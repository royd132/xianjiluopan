# 先机罗盘综合架构评审与重构路线

> 评审日期：2026-08-24  
> 评审范围：产品比赛表达、客服 Agent 开源结构、AutoSkill、主流 Harness、当前前后端代码与测试。  
> 结论性质：这是面向初赛与后续产品化的架构审计，不代表当前原型需要在提交前完成全部重构。

## 1. 总结结论

先机罗盘的业务方向切合“AI 市场洞察”：它已经围绕跨境商家的选品、定价、评论与供应链决策建立了证据链、决策卡、数据模式披露和人工审核。与单纯聊天机器人相比，这套产品更接近评委期待的“用数据代替直觉”。

当前最大问题不是技术能力不足，而是代码的职责边界没有跟上功能增长。运行编排、持久化、插件、工具治理、数据适配和前端交互分别集中在少数大文件中，使架构图看起来比代码本身更清晰。项目适合参加初赛，但若继续堆功能，复赛演示稳定性、团队协作效率和技术答辩可信度都会下降。

建议保留现有技术资产，不进行推倒重来：

- 保留领域模型、证据门禁、Real/Hybrid/Mock 合同、Run Ledger、Checkpoint、作用域工具注册、可逆安装、组件快照和人工激活；
- 将稳定的市场洞察业务内核与可替换能力分开；
- 把“策略阈值演进”和“可复用 Skill 演进”明确拆成两条能力线；
- 先做无行为变化的模块拆分，再补真正的 Skill Bank 和生产级异步执行。

## 3. 主要发现

### P1：Runtime 是事实上的总控类

`ForesightRuntime` 同时负责任务生命周期、进程内任务表、Provider 安装与恢复、组件快照、节点编排、结果缓存、卡片复核和演进调用。`backend/foresight/runtime.py:40` 定义总控类，`:56-57` 持有进程内任务状态，`:98` 开始管理 Provider，`:345` 开始管理节点执行，`:569` 又进入卡片复核；该文件已超过 560 行，并直接依赖 Agent、数据 Provider、演进、扩展系统、Harness 和领域模型。

风险：

- 修改数据源可能影响任务恢复；
- 修改人工复核可能触碰编排器；
- 无法在不启动完整 Runtime 的情况下单测应用服务；
- 后续引入 Worker 或消息队列时，没有清晰的任务端口可以替换。

结论：`ForesightRuntime` 应缩为用例协调器，不再持有 Provider 生命周期、SQL Store 和复核业务实现。

### P1：Harness 具有正确机制，但模块边界过密

`backend/foresight/harness.py` 在 `:43`、`:60`、`:299`、`:521`、`:537` 分别开始定义 `TraceWriter`、`MemoryStore`、`RunStore`、`CheckpointStore` 和 `AgentHarness`，`:678` 之后仍包含节点执行。它已经具备原型所需的恢复与审计能力，但不是一个可独立演进的 Harness 包。

风险：

- Durable Event、Checkpoint 和 Memory 的持久化规则互相缠绕；
- JSONL Trace 与 SQLite Run Event 同时存在，谁是权威事实源不明确；
- 无法独立替换存储、Telemetry 或执行器；
- “Harness”容易在答辩中被质疑为一个大工具类，而不是清晰的运行时协议。

建议把 Harness 收敛为会话与节点生命周期协议，由 Store、Event Log、Tool Runtime、Approval 和 Telemetry 分别实现。

### P1：当前还没有 AutoSkill 意义上的 Skill 系统

`backend/foresight/evolution.py:238` 的 `EvolutionEngine` 已实现候选策略，`:275` 进入 Validation/Holdout 评测，`:347` 才允许人工激活，这是有价值的策略治理系统；但其演进对象是门禁参数字典，不是可复用的任务技能。

AutoSkill 将 Skill 视为显式、可读、可编辑和可迁移的资产，并把交互服务与 Skill 演进拆成双循环。其核心流程是“抽取候选 -> 相似 Skill 检索 -> add/merge/discard -> 版本化存储”，使用时再执行查询改写、混合检索和阈值过滤。官方实现也将管理、交互、存储、向量索引和演进评测拆为独立模块。[AutoSkill 论文](https://arxiv.org/html/2603.01145)、[AutoSkill 核心实现](https://github.com/ECNU-ICALK/AutoSkill/blob/main/autoskill/README.md)

因此当前应区分：

- Policy Evolution：调整证据数、置信度、发布门槛等全局治理策略；
- Skill Evolution：沉淀某个市场、品类或决策任务的可复用流程与约束；
- Model Evolution：SFT、LoRA 或权重训练，当前不实现。

### P1：真实数据 Provider 是连接器集合，也是第二个总控模块

`backend/foresight/real_data_provider.py:103` 开始定义统一 Provider，`:214` 同时负责监控快照，`:273` 之后还承担 Hybrid/Real 采集，`:513` 后继续处理具体评论数据；全文件接近 930 行。真实数据越多，该文件越难测试和更换。

建议按数据源拆成 Connector，并通过统一 `MarketSignalSource` 协议输出标准化 Observation。汇率、评论、贸易、运价和供应链指数不应共享解析实现，只共享领域合同、缓存策略、时间新鲜度和错误语义。

### P1：单进程状态限制了实时性与可靠性

`backend/foresight/api.py:41` 在模块导入时创建全局 Runtime，`runtime.py:56-57` 使用 `boards` 与 `tasks` 字典保存活动任务。单机演示没有问题，但多 Worker 部署时，不同进程看不到对方的任务和 SSE 事件；进程重启后可恢复 Ledger，却不能自然恢复原订阅关系。

这不是初赛阻断项，但必须在技术路线中明确：

- API Gateway 不直接执行研究任务；
- Task Worker 从持久队列领取任务；
- Event Log 是进度事实源，SSE/WebSocket Gateway 只做投影；
- Connector 按数据源 SLA 调度，不能把所有“实时”都定义成同一分钟刷新。

### P1：前端已经成为单组件应用

`src/App.jsx:343` 开始的单一 `App` 组件约 940 行，`:344-376` 集中声明三十余项页面状态，`:412` 之后分散放置多个 API 请求，同时还承担 SSE/轮询、决策卡映射、监控、自进化和弹窗渲染；`src/styles.css` 也超过 450 行。继续增加实时告警、Skill 版本和数据源状态时，回归风险会迅速上升。

建议按业务 Feature 拆分，而不是按按钮或视觉区域机械拆分：`research-workspace`、`decision-cards`、`evidence`、`monitoring`、`evolution`、`runtime-status`。

### P2：测试覆盖与技术声明不匹配

目前测试集中在 API、Runtime 和 Extensions，能够证明主流程，但还不能证明以下主张：

- Connector 在字段变化、限流、超时、脏数据下仍满足合同；
- 中断、重启、重复投递和并发任务不会造成错误复用；
- Skill 检索、合并和晋级不会污染已有能力；
- 前端在 SSE 断线、任务失败和移动端下仍可完成核心流程；
- 决策卡确实改善商家决策时间或判断质量。

## 4. 开源项目对照结论

### 4.1 获奖项目优先看什么

Microsoft AI Agents Hackathon 2025 有公开、可核验的获奖名单。最佳总冠军 RiskWise 聚焦供应链风险，Apollo 使用协调者加专家 Agent、状态机和两阶段综合，TARIFFED! 则把复杂关税数据落入结构化 SQL，再由 Agent 与搜索工具形成可解释回答。这三项对先机罗盘的启示不是“多放几个 Agent”，而是业务问题、权威数据、专门能力和最终决策必须形成完整闭环。[Microsoft 官方获奖项目页](https://microsoft.github.io/AI_Agents_Hackathon/winners/)

其中最值得借鉴的是：

- RiskWise：围绕风险发现、影响分析和可视化决策构造端到端价值；
- Apollo：协调者只管理状态与合成，专家节点拥有清楚的输入输出；
- TARIFFED!：结构化事实先于生成，私有数据与开放数据采用不同 Grounding 通道。

“大型黑客松获奖”和“客服 Agent 权威开源”并不完全重合。公开客服仓库中，部分只是参赛作品，不能因为 README 写有 hackathon 就当作获奖权威。本评审只把已核验获奖案例用于比赛校准，把官方客服 Demo 用于代码结构参考。

### 4.2 客服 Agent 的可迁移结构

OpenAI 官方 Customer Service Agents Demo 把 Python 编排后端和 Next.js UI 分开，后端再按 `agents.py`、`context.py`、`guardrails.py`、`tools.py` 和演示数据划分职责。它适合展示“路由、专门 Agent、工具、Guardrail、Handoff”的最小结构，但官方也明确将其定位为 Demo，不能照搬为生产架构。[OpenAI Customer Service Agents Demo](https://github.com/openai/openai-cs-agents-demo)

客服系统中值得迁移到市场洞察的模式：

| 客服模式 | 先机罗盘对应设计 |
|---|---|
| 确定性安全预检 | 研究请求、市场、数据模式与数据许可预检 |
| Triage/Router | 按问题类型选择价格、评论、贸易或供应链工作流 |
| Retrieval 与 Generation 分离 | 先检索 Observation/Evidence，再生成 Decision Card |
| Handoff/人工升级 | 证据不足、冲突或高风险决策进入人工复核 |
| Audit Agent/Guardrail | 共享的 Decision Gate，不再增加一个自由生成 Agent |
| 渠道适配器 | 数据 Connector 与通知 Channel 分开 |

不应迁移的模式：把每个函数都包装成 Agent、让 Agent 自由聊天协商、用多 Agent 数量作为创新点。采集、清洗、汇率换算和阈值判断应优先采用确定性代码。

## 5. Skill 架构审阅

### 5.1 应借鉴的 AutoSkill 机制

1. 显式资产：每个 Skill 使用 `SKILL.md` 和机器可读元数据，内容可审计、可修改、可导出。
2. 双循环：在线研究只负责检索与应用 Skill；抽取、合并、评测和晋级异步运行，不增加主链路延迟。
3. 控制污染：候选应主要来自用户反馈、人工修正和成功案例，不把模型自己的回答当成可靠经验反复学习。
4. 混合检索：语义向量负责相似意图，BM25 负责市场代码、品类词和业务术语；Top-K 与最小阈值共同限制注入。
5. 版本治理：相似 Skill 优先 merge，保留身份和版本历史，避免复制出大量近义文件。
6. Replay 与 Promotion：候选 Skill 必须在固定案例集与 Holdout 上验证，人工批准后才进入生产可检索集合。

### 5.2 不应照搬的部分

- 不从每次研究会话自动抽取 Skill，只有明确纠错、稳定偏好或可重复成功流程才进入候选；
- 不把商品价格、汇率和短期趋势写进 Skill，它们属于有时间戳的 Observation；
- 不让 Skill 绕过 Evidence Gate、数据许可和人工审批；
- 不在初赛前引入复杂向量基础设施，当前规模可先用 SQLite 元数据、BM25 和可替换 Embedding 端口；
- 不把“自动生成了一个 Markdown 文件”宣传为已经实现自进化，必须同时有检索命中、版本、评测、晋级和回滚证据。

### 5.3 建议的 Skill 对象

```yaml
id: price-margin-safety
name: 跨市场毛利安全检查
description: 当定价建议涉及汇率、平台费、关税和物流成本时使用
version: 0.1.0
scope:
  markets: [BR, US]
  categories: ["*"]
triggers:
  - 定价
  - 毛利
  - 汇率波动
inputs:
  - observations
  - seller_constraints
outputs:
  - validation_findings
  - failure_conditions
evidence_policy: require_current_fx_and_cost_timestamp
status: candidate
```

首批 Skill 建议只做四个：

- `market-entry-evidence-check`：新品进入目标市场的证据完整性检查；
- `price-margin-safety`：汇率、费率、税费和物流波动下的毛利安全检查；
- `review-pain-localization`：区分目标市场评论、跨市场评论与可迁移痛点；
- `stale-signal-recompute`：关键 Observation 过期时触发局部重算而非复用旧结论。

## 6. Harness 综合审阅

### 6.1 DSH：借鉴事件与可逆装配，不照搬全部插件内核

DSH 的官方架构将模型适配、工具注册、会话日志和 Agent Loop 都视为插件，通过共享上下文、类型化事件和可逆 Effect 装配；它还区分 Durable Session Event、运行中的 Agent Event 和 Capability Event，并把模型可见上下文从 Append-only Session Log 投影出来。[DSH Architecture](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md)

当前项目已经借鉴了 Scope、Guard、Effect Stack、Provider Generation 和 Component Snapshot，方向正确。下一步最应该补的是：

- 明确唯一 Durable Event Log，Trace 和 UI 进度都从它投影；
- 区分 `Task`、`Turn`、`Step`、`NodeAttempt`，不要只保留节点状态；
- Tool 调用形成 pre-execute、execute、post-execute 生命周期；
- Profile 只用于装配 Provider、Model、Skill Set 和 Policy，不替换市场洞察状态机。

不建议采用“无特权核心”。先机罗盘需要稳定的领域合同、证据规则和发布门禁，这些应保持为不可被普通插件覆盖的 Trusted Kernel。

### 6.2 DeerFlow 2：借鉴 Gateway、Harness 包与受控子任务

DeerFlow 2 将 `backend/app` 与 `backend/packages/harness` 分开，并在仓库层面分离 backend、frontend、contracts、skills 和 tests；其 Harness 强调 Sandbox、Memory、Skills、Sub-agents、Gateway、Tracing 与长任务能力。[DeerFlow 2 官方仓库](https://github.com/bytedance/deer-flow)

适合先机罗盘的部分：

- API/Gateway 与 Harness Runtime 分离；
- 前后端共享稳定 Contracts；
- Skill 作为仓库一级资产，并有单独测试；
- 子任务并发有上限，失败可以局部恢复；
- 长任务拥有目标、事件、Checkpoint 和可观测性。

不适合当前阶段的部分：通用文件系统 Sandbox、任意代码执行、复杂长上下文压缩。市场洞察任务的核心上下文应是结构化 Observation 和 Evidence，不是无限增长的聊天记录。

### 6.3 Codex：借鉴 Core、Protocol、Execution 和 UI 的硬边界

Codex 将业务逻辑放在 `codex-core`，将协议类型放在低依赖的 `codex-protocol`，并明确协议层不承载实质业务逻辑；App Server 以 Thread、Turn、Item 建模生命周期，向 UI 提供双向协议、流式事件、审批和中断能力。执行、Sandbox、Skills、Hooks、存储与各类 UI 也分属独立包。[codex-core](https://github.com/openai/codex/blob/main/codex-rs/core/README.md)、[codex-protocol](https://github.com/openai/codex/blob/main/codex-rs/protocol/README.md)、[codex app-server](https://github.com/openai/codex/blob/main/codex-rs/app-server/README.md)

对本项目最直接的启示：

- `models.py` 不应继续同时充当领域模型和传输协议；
- API Schema 应是领域对象的投影，不反向控制领域实现；
- Task、Run、Event 和 Decision Card 要有稳定版本号；
- UI 只消费协议和投影，不读取 Runtime 内部结构；
- 高风险工具需要权限、审批和可重放的结果记录。

### 6.4 Claude Code：借鉴组件发现与渐进披露，谨慎谈核心实现

Claude Code 的公开仓库主要提供插件、Hook、Agent 和 Skill 结构，而不是完整核心 Harness 源码，因此不能像 DSH、DeerFlow 或 Codex 一样做内部实现级对照。其公开结构仍有两点值得借鉴：

- Plugin 下按 `agents/`、`skills/`、`hooks/`、`commands/` 和 `.mcp.json` 分离，并自动发现组件；
- Skill 采用 `SKILL.md` 加 `scripts/`、`references/`、`examples/` 的渐进披露，核心文件保持精简，详细资料按需加载。[Claude Code Plugin Structure](https://github.com/anthropics/claude-code/blob/main/plugins/plugin-dev/skills/plugin-structure/SKILL.md)

先机罗盘可采用相同的 Skill 文件布局，但 Skill 的触发、证据约束、评测和晋级规则必须由自己的领域运行时控制。

### 6.5 Harness 能力矩阵

| 能力 | 当前状态 | 目标状态 |
|---|---|---|
| Task/Run 持久化 | 已实现 | 保留并从 Runtime 解耦 |
| Checkpoint/Resume | 已实现节点级 | 增加幂等键、重复投递和失败注入测试 |
| Durable Event Log | 部分实现 | 统一 SQLite Event 与 JSONL Trace 的权威关系 |
| Tool Registry/Guard | 原型良好 | 拆为 Tool Catalog、Policy、Executor、Audit |
| Plugin 热更新 | Provider 已实现 | 只扩展稳定能力边界，不插件化业务内核 |
| Component Snapshot | 已实现 | 增加 Schema Version 与兼容检查 |
| Approval/HITL | 卡片级已实现 | 增加高风险工具调用审批 |
| Model Routing | 单一适配器 | Model Port + Provider Adapter + Retry/Circuit Breaker |
| Sandbox | 未实现 | 初赛不需要，未来仅用于可执行工具 |
| Context Compaction | 未实现 | 结构化摘要优先，暂不做通用压缩 |
| Skill Runtime | 未实现 | 检索、注入、版本、评测、晋级、回滚 |
| Queue/Multi-worker | 未实现 | 生产阶段引入 Broker 与 Worker |
| Telemetry | 本地 Trace | 统一 Metrics、Trace、Log 和业务指标 |

## 8. 分阶段重构路线

### 阶段 0：比赛提交前，0.5 天

- 保持运行代码不动；
- README 对外只声明已验证能力；
- 演示中突出一条真实证据链、一张决策卡和一个人工审核动作；
- 将 Skill 自进化明确列为下一阶段，不临时拼装假闭环。

验收：前后端 CI 全绿，Real/Hybrid/Mock 标签无误，演示教程可完整跑通。

### 阶段 1：无行为变化拆分，1 至 2 天

- 把 `api.py` 改为 App Factory 和依赖注入；
- 将 `App.jsx` 按 Feature 拆分，抽出 API Client 与 Task Hook；
- 把真实数据 Provider 按 Connector 拆文件；
- 为每个 Connector 增加统一合同测试。

验收：现有 API Snapshot、23 个后端测试和前端构建保持通过；增加 Connector Contract Tests。

### 阶段 2：Harness 收敛，2 至 4 天

- 从 `harness.py` 拆出 Run Store、Event Store、Checkpoint、Tool Runtime；
- 确定 SQLite Event Log 为权威源，JSONL 只作为导出或诊断 Sink；
- 引入 Task、Step、NodeAttempt、ToolCall 的版本化事件；
- 给 Runtime 注入协议，不再直接创建具体 Store 与 Provider；
- 增加取消、重启、重复投递、超时和组件版本不匹配测试。

验收：故障注入后结果不重复发布；同一幂等键不会创建两份研究任务；恢复沿用原 Component Snapshot。

### 阶段 3：Skill Bank 最小闭环，3 至 5 天

- 创建 `SkillArtifact`、文件 Store、混合检索和版本索引；
- 只从人工反馈、修正卡片和标记成功运行中抽取候选；
- 实现 add/merge/discard，候选默认不可用于生产；
- 用 Validation/Holdout 回放评估 Skill 对证据完整率、错误发布率和决策一致性的影响；
- 人工晋级后才加入 Active Registry，支持回滚。

验收：演示一条完整链路，从商家纠错到 Candidate Skill，再到评测、人工晋级和下一次任务命中；所有步骤有版本与审计记录。

### 阶段 4：生产实时化，按试点推进

- API Gateway、Task Worker、Scheduler 和 Event Projection 分离；
- SQLite 迁移到 PostgreSQL，任务进入持久队列；
- 按数据源定义 Freshness、Latency、Availability 和 Cost SLA；
- 汇率与价格使用短 TTL，贸易与供应链指数按发布频率更新；
- 采用局部失效和局部重算，不因一个源超时让整份报告失效；
- 建立来源授权、限流、熔断、降级和数据许可审计。

验收：SLA 看板能区分“数据源尚未发布”“抓取延迟”“缓存过期”和“模型处理延迟”，并在证据卡上显示数据发生时间与系统采集时间。

## 9. 比赛优先级

### 必须保住

- 数据模式和真实性披露；
- Evidence 到 Decision Card 的可追溯链；
- 目标市场、品类和时间范围；
- 证据不足时拒绝或降级；
- 人工审核与失效条件；
- 一键可运行的演示路径。

### 最能打动技术评委

- 用 Run Ledger 和 Component Snapshot 证明可恢复与热更新是实装；
- 用共享 Decision Gate 证明线上与回放采用同一规则；
- 坦诚展示 Policy Evolution 与 Skill Evolution 的区别；
- 展示目标目录、迁移阶段与清晰的能力边界。

### 最能打动真实商家

- 不强调 Agent 数量，强调少做一次错误备货或错误定价；
- 决策卡同时展示收益假设、证据、风险、失效条件和下一步动作；
- 明确汇率、评论、运费和贸易数据分别多快更新；
- 允许商家纠错，并让系统说明这次纠错以后会在哪类任务中复用。

## 10. 最终技术判断

当前架构不是方向错误，而是原型期功能快速增长后形成了“概念先进、代码聚集”的不对称。最合理的路线不是切换到某一个通用 Harness，也不是复制某个客服 Agent 仓库，而是形成自己的组合：

```text
稳定的市场洞察 Domain Kernel
+ 可恢复、可审计的 Task Harness
+ 按源隔离的实时 Data Connectors
+ AutoSkill 式可治理 Skill Bank
+ 不可绕过的 Evidence/Approval Gates
```

完成阶段 1 和阶段 2 后，代码结构会与已有架构图一致；完成阶段 3 后，“自进化”才从策略参数治理扩展为商家可感知的经验复用。这个顺序既保住比赛演示，也给后续真实产品留下足够坚实的增长空间。
